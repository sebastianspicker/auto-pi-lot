# pi-graph review: what auto-pi-lot should inherit

Review date: 2026-09-22. Source: a local `pi-graph` checkout (sibling of this repository).

## Recommendation

Adopt the predecessor's **authority boundaries, durable transitions, scoped delegation,
and evidence tests**. Build a smaller runtime around those ideas. Do not transplant its
complete controller, research framework, compatibility history, or provider qualification system.

This is already a substantial implementation of the same product: its package is named
`auto-pi-lot`, it uses Pi SDK sessions, and it executes both preplanned and runtime child
graphs through one root run. It is a useful reference implementation and source of test
scenarios, rather than an unrelated prototype. Its local mechanisms are much better
established than its live coding effectiveness.

The most important addition to our plan is to distinguish **node execution from node
acceptance**, and **request reservation from possible external dispatch**. Both distinctions
need explicit state transitions, not conventions in agent prompts.

This document recommends changes to future implementation. It does not import predecessor
code, modify the predecessor, or claim the current auto-pi-lot scaffold implements these features.

## Patterns to adopt

### 1. Task intake owns one durable run from the beginning

Persist objective, immutable acceptance requirements, request identity, baseline and allowance
before planning. Clarifications and repairs belong to that run. Reuse a previously accepted
plan after restart instead of buying another plan or resetting the budget.

The predecessor binds duplicate requests to the same run, rejects conflicting reuse, stores
structured questions, and replays settled planner submissions across publication crashes.
Adopt those semantics; replace its retained-run scan with an indexed request lookup.

Sources: [task workflow](../../../pi-graph/src/application/tasks/workflow.ts) (36–115, 119–152),
[planning replay](../../../pi-graph/src/application/tasks/replay-planning.ts) (17–77).
Tests: [task lifecycle](../../../pi-graph/test/execution/task-workflow.test.mjs).

### 2. Graphs are validated data; plans cannot grant authority

Validate more than DAG shape: requirement coverage, declared artifact producers, direct
dependencies, role/model permissions, write scope, downstream verification, and immutable
root intent. A planner must not make a task easier by removing acceptance criteria.

For our contracts, add a requirement registry and explicit artifact bindings. Use node kinds
such as agent and host check, rather than assigning every operation to a model. A verifier
agent may interpret failures, but executing a configured check is a deterministic host action.

Sources: [graph validation](../../../pi-graph/src/domain/contracts/graph-validation.ts) (53–218),
[node-kind validation](../../../pi-graph/src/domain/contracts/graph-schema.ts) (4–29).

### 3. Recursive graphs share one scheduler and root account

The predecessor projects graph-local node IDs into one execution space while retaining graph
ownership separately. It suspends parents, admits descendants against root limits, and returns
typed results to a fresh parent segment. It does not launch an independent Pi subagent scheduler.

Adopt the single scheduler and cumulative admission. Keep our depth limit at 2; the predecessor
defaults to 3 below the root. Child budget limits should be reservations or ceilings inside the
root account, never independent replenishable allowances. Charge planning, failed/replaced nodes,
parent continuation and repair as well as successful leaf work.

Sources: [hierarchy projection](../../../pi-graph/src/domain/graph/hierarchy.ts) (8–74),
[hierarchy scheduling](../../../pi-graph/src/application/execution/graph-scheduling.ts) (80–109),
[suspension](../../../pi-graph/src/application/execution/graph-suspension.ts) (8–87),
[recursive design](../../../pi-graph/docs/adr/0025-recursive-subgraphs.md).
Tests: [subgraph execution](../../../pi-graph/test/execution/subgraphs.test.mjs).

### 4. Delegation is an explicit capability, with a complete return contract

Freeze the delegation ceiling before the parent runs. A request includes objective, allowed
models/checks/tools, workspace scope, inputs, output contracts and acceptance criteria. Bind
the child to immutable root requirements. Persist its identity before planning; deliver and
consume its result idempotently.

Adapt one default: `nodeDelegationScope` allows all configured model profiles and, for an
exclusive node, all configured check profiles unless explicitly narrowed. That is an intentional
host policy, not proof of a permission bypass. Our design should require an explicit per-node
delegation ceiling so the phrase “inherits parent authority” has one precise meaning.

Sources: [delegation validation](../../../pi-graph/src/domain/contracts/delegation.ts) (71–124),
[scope defaults](../../../pi-graph/src/domain/contracts/subgraphs.ts) (11–23),
[runtime delegation](../../../pi-graph/src/application/execution/runtime-delegation.ts) (23–73).

### 5. Closed Pi sessions and request-scoped tools

Use an explicit resource loader and host-defined tool callbacks. Ordinary worker sessions
must not silently discover the user's ambient extensions or gain normal CLI tool authority.
Load relevant repository instructions deliberately and retain their provenance.

The predecessor disables built-in tools, ambient resources, SDK retries and independent
compaction in graph sessions. Its tools exist only when a host callback is granted, and
submission/delegation crosses a host gate. Port this boundary with compatibility tests for
our newer pinned SDK (`0.87.0` versus predecessor `0.85.1`), not by assuming signatures match.

Sources: [closed loader](../../../pi-graph/src/adapters/pi/loader.ts),
[SDK construction](../../../pi-graph/src/adapters/pi/adapter.ts) (456–480),
[tool construction](../../../pi-graph/src/adapters/pi/tools.ts) (34–53, 253–277).
Tests: [SDK adapter](../../../pi-graph/test/adapters/agents.test.mjs),
[delegation adapter](../../../pi-graph/test/adapters/delegation.test.mjs).

### 6. Exact route identity and final-payload admission

Resolve exact provider/model/API references and freeze them per attempt. Fallback must be
explicit, visible and recorded. Inspect the final serialized provider payload, because the SDK
may add material after application context assembly. Reserve allowance before dispatch and
avoid hidden retry loops that bypass accounting.

Keep unknown usage separate from measured zero. Missing cache counters do not demonstrate
cache hits, free requests, or savings. For v1, implement limits and honest observations before
building elaborate pricing and cache qualification.

Sources: [route resolution](../../../pi-graph/src/application/models/resolve.ts) (224–259),
[request boundary](../../../pi-graph/src/adapters/pi/request-boundary.ts) (95–146, 177–225),
[usage observation](../../../pi-graph/src/adapters/pi/provider-usage.ts) (70–107).
Tests: [provider observations](../../../pi-graph/test/adapters/provider-observation.test.mjs).

### 7. Typed loops and checks available during implementation

Expose an allowed `request_check` operation so an implementer can run a bounded check,
inspect its evidence and repair within the same session. Keep final verification and independent
review separate. Distinguish transport retry, schema repair, semantic repair, diagnosis,
continuation and replan; all consume the existing run's limits.

Repeated actions should require a new hypothesis and expected observation rather than a
generic “try again” prompt. Applied edits must be preserved and repaired from current state,
not replayed as if the previous attempt never happened.

Sources: [iterative checks](../../../pi-graph/src/application/execution/iterative-check.ts) (9–108),
[recovery classification](../../../pi-graph/src/domain/planning.ts) (53–121),
[iterative-check ADR](../../../pi-graph/docs/adr/0024-iterative-host-checks.md).
Tests: [autonomous workflow](../../../pi-graph/test/execution/autonomous-workflow.test.mjs).

### 8. Evidence is host-owned and bound to exact inputs

An implementation submission is not a passing check. Retain check receipts with source,
environment, profile and input identities. Reject stale evidence. Child success is provisional
until its output contract and checks pass; root acceptance still requires final checks and review.

Our current `NodeResult` evidence strings are only a scaffold. Replace them with typed evidence
references and a separate worker proposal / supervisor acceptance contract before real execution.

Sources: [evidence validity](../../../pi-graph/src/application/execution/evidence-validity.ts)
(12–78, 106–149), [child boundary](../../../pi-graph/src/application/execution/graph-boundary.ts)
(36–111), [final acceptance](../../../pi-graph/src/application/execution/finish.ts) (76–139).

### 9. Transactional intent and honest external-effect recovery

Adopt short SQLite transactions, atomic account admission, immutable artifacts, checksum-verified
migrations, and a journal of intent/completion for effects. Freeze attempt identity and reject
stale results. Crash tests should target both sides of each commit boundary.

The predecessor closes the gap between a committed controller phase and a LangGraph checkpoint
by storing a transition patch/event and binding checkpoint bytes to it. This is valuable when
using that framework, but it is also integration work our first runtime can avoid by choosing one
durable state machine. Neither design makes arbitrary shell or remote effects exactly once.

Sources: [transactional phases](../../../pi-graph/src/adapters/sqlite/transactions.ts) (9–29),
[checkpoint bindings](../../../pi-graph/src/adapters/sqlite/checkpoints.ts) (174–190, 243–287),
[workspace journal](../../../pi-graph/src/adapters/workspace/workspace.ts) (288–440),
[command receipts](../../../pi-graph/src/adapters/workspace/commands.ts) (241–384).

### 10. One context owner, explicit omissions and retrievable reductions

Keep stable policy separate from changing observations. Preserve mandatory obligations;
mask or retrieve large observations through immutable artifacts. Record what was included,
omitted or reduced. Continue only complete, supported tool exchanges.

Some optional context can be omitted without an artifact reference; an omission manifest
does not by itself preserve the omitted bytes. Require persisted references whenever we
claim a reduction is reversible.

Start with compact task packets, artifact references and a minimal final-payload admission
check. Defer elaborate cache epochs and portable continuation until needed. The predecessor's
conservative byte estimate is explicitly an estimate and can reject contexts a provider
would actually fit.

Sources: [context compiler](../../../pi-graph/src/application/context/compiler.ts) (72–105),
[context policy](../../../pi-graph/src/domain/policy/context.ts) (194–252),
[continuation](../../../pi-graph/src/adapters/pi/continuation.ts) (4–76),
[admission estimate](../../../pi-graph/src/application/context/request-admission.ts) (16–46).

### 11. Graph-mode UX preserves identity and unsent input

Capture only operator input, bind mode/run identity to the repository, and restore by querying
durable status without redispatch. Keep “mode off” distinct from “cancel.” If a busy run cannot
accept input, preserve the draft visibly rather than losing it or silently making a new task.

Adopt the behavior, but keep our CLI/extension thin clients of the supervisor. The predecessor
spawns CLI operations; our detached-supervisor lifetime is a deliberate architecture difference.
Its JSON editor setup is explicit but cumbersome. We can offer a small typed setup flow while
preserving operator-owned checks and displaying what will execute.

Sources: [input routing](../../../pi-graph/src/entrypoints/pi/graph-mode.ts) (60–95, 117–195),
[setup wizard](../../../pi-graph/src/entrypoints/pi/setup-wizard.ts) (56–165),
[framed events](../../../pi-graph/src/entrypoints/pi/event-stream.ts) (23–62).
Tests: [graph-mode behavior](../../../pi-graph/test/operator/graph-mode.test.mjs),
[onboarding](../../../pi-graph/test/operator/graph-onboarding.test.mjs).

### 12. Real local effects under fake reasoning, then small live evaluations

Use fake model decisions with real temporary repositories, commands and SQLite to test
orchestration deterministically. Add adversarial mutations to check that acceptance tests can
detect broken solutions. Keep hidden evaluation oracles outside worker grants. Count failed
attempts and cancellation cost in comparisons.

Also run a small, explicitly authorized live coding corpus early. The predecessor records
only 2 of 12 task trials passing in one historical focused live exercise. This does not measure
the current tree or prove that graphs are worse; it does show that a large green local suite
cannot establish model effectiveness.

Sources: [test harness](../../../pi-graph/test/helpers/harness.mjs) (19–160),
[mutant oracle checks](../../../pi-graph/test/evaluation/research-aligned-24-corpus.test.mjs)
(28–60), [outcome accounting](../../../pi-graph/src/application/reporting/outcome-metrics.ts)
(26–59, 192–225), [historical live results](../../../pi-graph/docs/current-evidence.md) (13–19).

## Confirmed defect and incomplete behavior to avoid

### High priority: a known pre-dispatch failure can permanently block the account

`uncertainModelCall` changes both admitted and dispatched requests to `uncertain`. For the
admitted case it emits `model_call.cancelled_before_dispatch`, but account calculations still
retain an uncertain reservation. New admission fails with `RUN_COMPLETION_UNCERTAIN`.
Operator reconciliation requires a dispatched call, so it rejects this same record.

The real Pi boundary can reach the state: payload admission succeeds, then manifest persistence
fails before dispatch. An offline fake stream reproduced that sequence. A second reproduction
showed that new admission, direct settlement, and reconciliation all fail; the final row remains
uncertain. This is an availability/recovery defect, not an assertion about remote billing.

For auto-pi-lot, model the transition explicitly:

```text
reserved ── known pre-dispatch stop ──> released / not-dispatched
reserved ── dispatch intent ─────────> potentially-dispatched
potentially-dispatched ── receipt ───> settled
potentially-dispatched ── unknown ───> reconciliation-required
```

Release reservations only when the host proves the provider dispatch boundary was not crossed.
Once it may have been crossed, preserve conservative accounting until reconciliation. Make
release idempotent and test cancellation, manifest failure and deadline expiry at that boundary.

Sources: [call state change](../../../pi-graph/src/adapters/sqlite/model-calls.ts) (151–170),
[reconciliation gate](../../../pi-graph/src/adapters/sqlite/reconciliation.ts) (80–82),
[Pi admission/dispatch](../../../pi-graph/src/adapters/pi/request-boundary.ts) (222–224, 285–293).
Offline reproductions are retained next to the [verification record](pi-graph-2026-09-22/verification.json).

Run either with the predecessor's pinned Node 24 and a built checkout argument. The scripts
create and remove their own temporary database, print observations, and make no provider calls:
[accounting reproduction](pi-graph-2026-09-22/reproduce-cancel-before-dispatch.mjs),
[request-boundary reproduction](pi-graph-2026-09-22/reproduce-request-boundary.mjs).

### Medium priority: child-boundary failures do not have complete recovery semantics

When child-boundary checks or review fail, `advanceGraphHierarchy` generally converts the
exception to `blocked`; the workflow routes that state to finish. It does not enter the same
bounded child repair path used for ordinary task failures. This is a documented incomplete
capability, not a claim that the code silently accepts a failed child.

Before declaring recursive execution complete, give boundary failures typed dispositions:
repairable check/review failure, missing input, policy denial, exhausted allowance and uncertain
effects. Only the first class should automatically repair. Persist questions and failures against
the full graph/node path and preserve sibling success. Do not require success at every boundary
without also designing the failure route.

Sources: [child verification](../../../pi-graph/src/application/execution/graph-boundary.ts)
(45–80), [catch-to-blocked](../../../pi-graph/src/application/execution/graph-scheduling.ts)
(47–50, 74), [workflow routing](../../../pi-graph/src/adapters/workflow/state-graph.ts) (19–27, 83–87).

## How this changes our implementation sequence

1. **Contracts and state first:** wire versions; immutable root requirements; agent/check node
   kinds; scoped delegation; separate result proposal, check receipt and acceptance record.
   Include released reservation versus uncertain dispatch states from the start.
2. **Sequential durable slice:** one root run and account spanning intake, planning, checks
   and review. SQLite state/event transactions, idempotent admission, fake workers, exact
   model route, controlled Pi resources, a final serialized-payload limit check, and explicit
   reserve/dispatch/settle boundaries with no hidden retries. These precede any live calls.
   Use one small durable runtime; defer framework adoption.
3. **One useful coding path:** preserve operator changes, execute isolated edits, run host-owned
   checks during implementation, integrate serially, and verify the integrated revision.
   Start with one writer; separate worktrees become essential before concurrent writers.
4. **Early live evidence:** a small fixed coding corpus, known checks, bounded request budget,
   failed-task accounting and comparison with a single Pi session. No automatic dispatch
   is authorized by this review.
5. **Child, then grandchild graphs:** persist spawn and suspension, release permits, reserve
   root budget, validate typed child returns, resume fresh parent segments. Test cancellation,
   clarification, failed child review, unplanned descendants and every commit/reopen boundary.
6. **Only after that:** context reduction, caching, scheduling optimization, UI visualization
   and optional integrations, each with a measurable need and a bounded acceptance test.

No Neo4j, vector store, Redis, distributed queue, second agent scheduler or fleet daemon is
needed for this first target. SQLite and artifact files remain a good fit. Evaluate a small
SQLite adapter or `pi-durable` independently; importing the predecessor's 19 migrations is
appropriate only if we explicitly choose compatibility with its existing run databases.

## Adoption checklist

| Import candidate | First regression to bring with it |
| --- | --- |
| Task intake / clarification semantics | Same request and duplicate answer cannot create a new run or replenish allowance |
| Graph validation / root criteria | Planner cannot remove verification or create an unbound artifact dependency |
| Closed Pi adapter | Ambient extension canary never loads; exposed tools equal the frozen grant |
| Request accounting | Failure before dispatch releases once; failure after possible dispatch stays uncertain |
| Worker result protocol | Invalid submission and stale evidence cannot become acceptance |
| Effect journal | Reopen after applied edit preserves it without repeating the mutation |
| Parent suspension | All worker slots can wait without starving ready descendants |
| Child delivery | Restart cannot redeliver a result, replay parent edits or reset repair budget |
| Child boundary recovery | Failed child review repairs or reports a typed terminal result under the same allowance |
| Graph mode | Off does not cancel; busy input is preserved; restore never redispatches |
| Integration | Two individually passing patches still require checks on the combined tree |

Port small mechanisms together with their meaningful tests. Preserve our package boundaries
and simplify contracts deliberately; importing the predecessor's public Controller facade
would effectively import the old product and its compatibility obligations.
